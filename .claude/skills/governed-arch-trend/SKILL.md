# governed-arch-trend — 동향 정기 감시

① 동향수집을 매일 무인으로 돌리는 확장이다. 이름의 governed는 **사람이 검수한 것만 refs에 들어간다**는 뜻이다.

## 하는 일과 하지 않는 일

| 한다 | 하지 않는다 |
|---|---|
| 수집이 끝난 영역의 선택지 변화와 새 선택지 후보를 걸러 후보 큐에 쌓는다 | refs · 비교표를 직접 고치기 |
| 후보마다 출처 · 날짜 · 주장 단위 등급 · 걸리는 평가 축을 붙인다 | 판정(상 · 중 · 하) 내기 |
| URL이 실제로 열리는지 확인한다 | 열리지 않는 URL을 후보로 올리기 |
| 후보가 PDF거나 본문에 백서 · 보고서 PDF가 걸려 있으면 `files/`로 내려받아 노트에 경로를 적는다 | JS 렌더링 자료실 긁기, 25MB 초과 파일 받기 |
| 주 1회 요약 메일을 개인 메일로 보낸다 | 회사 정보 · `private/` 읽기 |

## 구성

| 위치 | 내용 | 공개 |
|---|---|---|
| `.claude/skills/governed-arch-trend/` | 이 지침, `config/`(소스 · 별칭), `scripts/` | 공개 저장소 |
| `refs/*.md` | 감시 대상의 원천 — 「선택지 요약」 표가 있는 영역만 감시 | 공개 저장소 |
| 상태 폴더 `GAT_STATE`(기본 `~/한양대학교/governed-arch-trend`) | `_data/`(수집 · 매칭 · 큐레이션 · seen · files_ledger), `queue/{날짜}.md`, `files/{날짜}/`(내려받은 PDF) | 비공개 리포 `LoveEvaLee/harness-governed-arch-trend` |

VM은 공개 저장소를 읽기만 한다. 그래서 refs의 감시 대상은 유경이 검수해 push한 것만 VM에 닿는다.

## 흐름 (`scripts/run_daily.sh`)

1. `build_watch.py` — refs 「선택지 요약」에서 선택지를 뽑고 `config/aliases.json` 별칭을 붙여 `_data/watch.json`
2. `collect.py` — `config/sources.json`의 피드 · GitHub 릴리스 · 자료 페이지(`doc_pages`, 정적 HTML의 PDF 링크) 수집 → `_data/collected/{날짜}.json` (seen으로 중복 제거)
3. `match.py` — 선택지 별칭 매칭(「선택지」 풀)과 영역 키워드 매칭(「영역 키워드」 풀, 영역당 15건까지) → `_data/matched/{날짜}.json`
4. 큐레이션(headless Claude, 아래 규칙) → `_data/digests/{날짜}.json`
5. `render_queue.py` — URL 확인 후 `queue/{날짜}.md`. 이때 후보가 PDF거나 본문에 백서류 PDF 링크(whitepaper · report · guide · 백서 · 보고서 등)가 있으면 `files/{날짜}/`로 내려받고(후보당 2개 · 하루 5개 · 파일당 25MB 상한, `_data/files_ledger.json`으로 중복 차단) 노트의 「자료(내려받음)」 행에 링크를 적는다 — 다운로드 실패는 큐 노트 생성을 막지 않는다
6. 월요일에는 `weekly_mail.py` — 지난 7일 요약을 개인 메일로

## 큐레이션 규칙 (4단계 — headless Claude가 따른다)

**입력.** `_data/matched/{날짜}.json`의 `items[]`, 그리고 항목의 `area_file`(refs 파일). refs는 읽기만 한다.

**버린다.** 감시 선택지 · 영역과 실제로 관계없는 것(별칭이 우연히 걸린 것), 이미 refs에 같은 내용이 있는 것, 홍보 · 채용 글, B 출처(기업 기술 블로그)의 도입 · 운영 사례가 아닌 글. 대부분 버려지는 것이 정상이다.

**남긴 항목마다 `kind`를 하나 고른다.**

| kind | 언제 |
|---|---|
| 갱신 | refs에 있는 근거의 사실이 바뀌었다 — GA · 지원 종료 · 가격 · 한도 · 버전 정책. `related_evidence`에 바뀌는 근거를 적는다(예: "AWS Glue 근거 3") |
| 새 근거 | 그 선택지의 「비어 있는 것」에 적힌 축 · 보는 항목을 채운다 |
| 새 선택지 | 이 영역에 refs에 없는 선택지 후보가 나왔다(「영역 키워드」 풀에서 주로 나온다) |

**등급은 ① 동향수집 SKILL.md와 같다 — 주장 단위.** 출처 등급(`source_grade`)을 출발점으로 하되, 벤더가 자기 제품이 낫다고 하는 비교 주장은 D. D가 되는 후보는 올리지 않는다. 애매하면 낮은 쪽.

**날짜.** 피드의 `published`를 쓴다. 없으면 "날짜 없음"이라 적고, 공식 문서 · 릴리스 노트면 「상시 갱신 — 확인 {날짜} 기준」, 블로그 · 사례면 D로 보고 올리지 않는다. 발행이 기준(AI · 에이전트 플랫폼 12개월, 나머지 24개월)보다 오래되면 「오래됨」.

**쓰지 않는다.** 피드 요약에 없는 내용을 추론해서 채우지 않는다 — 모르는 칸은 〔미정〕. 원문을 길게 옮기지 않고 요지만 한국어로 쓴다.

**출력 스키마** — `_data/digests/{날짜}.json`

```json
{
  "date": "YYYY-MM-DD",
  "collected": 0, "pooled": 0, "dropped": 0,
  "candidates": [
    {
      "id": "항목 id 그대로", "area": "ETL오케스트레이션",
      "kind": "갱신 | 새 근거 | 새 선택지",
      "option": "refs의 선택지 이름 그대로 (새 선택지면 null)",
      "title_ko": "한 줄 제목", "url": "항목 url 그대로", "source_name": "소스 이름 그대로",
      "date_info": "발행 YYYY-MM-DD · 확인 YYYY-MM-DD · 오래됨 아님",
      "grade": "A | B | C", "grade_claim": "이 등급으로 받치는 주장 한 줄",
      "summary_ko": "요지 한두 문장", "axes": ["축 — 보는 항목"],
      "related_evidence": "선택지 근거 N 또는 null",
      "why_ko": "왜 후보인가 — 무엇이 바뀌었나 / 어느 빈칸을 채우나 / 어떤 새 선택지인가"
    }
  ]
}
```

후보가 없어도 `candidates: []`로 파일을 쓴다. 영역마다 하루 10건을 넘기지 않는다.

## 후보 반영 (사람이 부를 때)

"후보 반영해줘" → `queue/` 노트에서 체크(`- [x]`)된 후보만 골라 ① 동향수집 지침대로 refs에 넣는다: URL 재확인, 선택지당 상한 10건, 빈 축 우선, 「비어 있는 것」 갱신, `refs/비교표.md` 갱신, 결과 파일을 열어 센 표. 반영한 id는 `_data/applied.json`에 남긴다. 체크되지 않은 후보는 건드리지 않는다.

## 하지 않을 것

- refs · 비교표 · `layouts/` · `rubric/`을 무인으로 고치기
- 회사 정보를 검색어 · 설정에 넣기, `private/` 읽기
- 판정 내기, 벤더 자기 우월 주장을 사실로 옮기기
- 수집 범위(① 동향수집 「수집 범위」) 밖 출처를 소스에 추가하기
